# v1.16.0 · 应用内检查更新

> 起因：用户在手机上打开 App，期待「有新版本」的提示，但什么都没发生。
> 查下来不是提示被关掉了，而是**这个功能从来没写过**——App 里没有任何一行代码问过
> 「线上最新是哪个版本」。v1.15.0 之前的更新方式只有一种：自己去 GitHub 下载 APK 覆盖安装。

## 一、这次加了什么

| 入口 | 行为 |
|---|---|
| 开屏（延迟 3 秒） | 静默查一次；**只有真有新版**才弹窗，其余情况一声不响 |
| 我的 → 版本（点整行） | 手动检查，必有回话：有新版的弹窗 / 「已是最新 v1.16.0」/ 「查不到更新」+ 发布页快捷入口 |
| 弹窗里的「去下载」 | 用系统浏览器打开 APK 直链，下完点安装即可覆盖 |
| 弹窗里的「以后再说」 | 该版本 **3 天内**不再弹（手动检查不受此限） |

弹窗同时写清了安装动作：「点去下载 → 下完点安装 → 系统问是否允许安装时选允许」，
以及「不用卸载旧版，数据不会丢」——这是用户最怕的一件事，得写在按钮旁边而不是文档里。

## 二、机制与取舍

- **问的是 GitHub Release API**：`GET /repos/xia259214-beep/morning-app/releases/latest`，
  取 `tag_name` 比版本、从 `assets` 里挑第一个 `.apk` 的 `browser_download_url`。
  没挂 APK 时退回 release 页面，不会给出空链接。
- **零第三方依赖**：用 `dart:io` 的 HttpClient。为了一个「有没有新版」的判断题引一整个
  更新 SDK 不划算，也违背这个项目一直的零依赖约定。
- **节流 12 小时**：开屏才查，且半天最多一次。手机每早开一次，实际就是「一天一问」。
- **失败静默**：断网、GitHub 访问不稳、接口限流一律吞掉，不弹错误、不打断。早上七点
  被人叫醒的时候没人想看「网络异常」。失败后 1 小时内不再重试，避免每次开屏都卡超时。
- **不打扰晨间流程**：首次引导没走完、或正处在晨间流程页（被闹钟叫醒）时，本次不检查。
- **版本比较按数字逐段比**：`1.9.0 < 1.10.0`（字符串比较会判反，这是最容易踩的坑）；
  `v` 前缀、`+构建号`、`-预发布后缀` 都不参与比较。
- **不再自动装**：Android 不允许应用静默安装自己的更新（需要用户点系统安装器）。
  「应用内检查 + 浏览器下载 + 系统安装器」是侧载分发的标准路径，也是唯一不需要
  危险权限的路径。

## 六、真机上抓到并修掉的三处

截图一看就露的问题，单测抓不到：

1. **弹窗背景太透**：原先用 `AppColor.glassPanel`（半透明），说明文字和底下首页的字叠在一起，
   一片糊。改成不透明的 `AppColor.card` + 描边。更新说明是要被读的，这里不该用玻璃质感。
2. **说明区被硬切在半行上**：长说明放在 200px 高的可滚区里，边缘裁在文字中间，看着像渲染错误。
   改成带边框浅底的容器（`bg` 60% + `line` 描边 + 12px 圆角），一眼能看出「这块能滚」。
3. **点弹窗外面就关掉**：`barrierDismissible` 默认 true，误触关掉不记「以后再说」，下次开屏又弹，
   反而更烦。改成 `barrierDismissible: false`，要关就点「以后再说 / 知道了」。

顺带确认了一条原本只是设计意图的行为：**按返回键关弹窗 = 「以后再说」**（会写 3 天跳过期）。
实测时正是被它挡了几次开屏检查，一开始误以为网络不通——查本地存储才看到
`updateSkipped=1.16.0`。行为本身合理，但值得记一笔。

## 八、更新方式（用户视角，发版时可直接贴到 release 说明）

1. 打开「晨序MORNING」→ 我的 → 版本，点一下；或直接开 App 等几秒
2. 看到「有新版本」→ 点「去下载」
3. 浏览器下完 APK，点它 → 系统问「是否允许安装未知应用」，选允许
4. 装完直接打开，闹钟和记录都还在

> 旧版本（v1.15.0 及更早）里没有这段代码，**必须手动更新一次**，之后才会有提示。

## 九、v1.16.2：撞到 GitHub 的 API 限额

发完 v1.16.1 核对线上版本时，`curl` 直接吃到：

```
HTTP 403 {"message":"API rate limit exceeded for ..."}
```

未登录的 GitHub API 每小时只给 **60 次，而且是按出口 IP 算**——家里几台设备、或者用户
手快连点几次「检查更新」，配额说没就没。配额一满，App 的表现就是「查不到更新」，
跟断网一模一样，用户完全无法区分。

修法：`fetchLatest` 变成两段。先走 API（能拿到更新说明），失败就退到一条**不消耗配额**的
路径——请求 HTML 的 `/releases/latest` 且不跟随跳转，只读 302 的 `Location` 拿到 tag：

```
https://github.com/xia259214-beep/morning-app/releases/latest
  → 302 Location: https://github.com/xia259214-beep/morning-app/releases/tag/v1.16.1
```

这条路径拿不到更新说明、也拿不到 APK 直链（资产名带版本号，猜错就是 404），所以在这种
情况下把「去下载」改成「打开发布页」，让用户在页面上点 APK——宁可多一次点击，也不给错链接。
`tagFromReleaseLocation` 对认不出的形状一律返回空串，宁可不提示。

实测（正好在限额期内）：兜底路径 1 秒内拿到 `v1.16.1`，跳转地址正确；新增 3 组单测覆盖
标准跳转 / 带查询串与片段 / 跳错地方。
